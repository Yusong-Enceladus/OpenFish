# Agent Note: 将 OpenCodex 构建为 DSH 产品组合

Status: implemented

[English](2026-08-17-opencodex-on-dsh.md) | 中文

## 问题

DSH 已经拥有开放式 Codex 实现所需的 agent 运行时、仅追加会话日志、工具、审批、持久化、提供方路由、Host RPC、Web 客户端和插件生命周期。Parity 分支还添加了 X CLI、原生应用壳、`x-native` 桥接、复制的界面字符串以及若干能力包。其中一部分新增内容正确复用了 DSH，另一部分只能证明某个命令、资源或包存在。若把这些产物当作第二套产品栈，就会重复状态、协议和生命周期行为，最终无法维持行为一致性。

在继续客户端工作前，OpenCodex 需要一个产品定义和一条所有权规则。比较方向是用 DSH 对照 Codex：Codex 已提供而 DSH 缺少的功能必须在 DSH 插件架构内实现。被扩展的组件不是 Codex，DSH 当前的功能集合也不是上限。

## 决策

### 产品不变量

OpenCodex 是发布时统一 ChatGPT 桌面应用内的 Codex 桌面工作面、Codex CLI、iPhone、远程和语音产品，以及发布时 DSH Web 与 `anchored` 组合在功能、信息架构和关键交互上的严格超集。对照目标是 Codex 产品工作面，而不是碰巧位于同一桌面应用中的无关 ChatGPT 对话工作面。用户能在任一基线中观察或依赖的能力都属于范围，除非本文明确排除。已捕获的 parity 清单是可追溯性快照，不能替代发布前刷新基线。

OpenCodex 使用自己的名称和资产，Codex 则提供行为、信息架构和交互参考。核心界面与工作流必须进行并排视觉和行为对照；复制的本地化字符串、命令帮助、类名和包存在性都不能证明一致性。

### 运行时所有权

DSH 是 OpenCodex 运行时，而不是隐藏在平行 X 运行时之后的依赖。新行为遵循 [DSH 架构](../../../../docs/architecture.md)中的扩展规则和 [GUI 分层决策](../../implemented/architecture/2026-07-19-gui-layering-and-rpc-protocol.md)中已有的 Host／Client 划分。

| 关注点 | 权威所有者 | 客户端规则 |
|---|---|---|
| 会话、轮次、消息、工具调用、审批和模型历史 | 现有 DSH 服务与仅追加会话日志 | 渲染投影并发送意图；绝不维护第二份持久化真源。 |
| 业务操作 | 所属 DSH 服务，通过 Typert 或现有 `/api` Host 组合暴露 | 不得添加业务方法的原生专用副本。 |
| 新增可移植能力 | 当各角色独立演进时，由 Service Definition、Service Provider 和 Consumer 角色组成完整的 DSH 能力 seam | 每个客户端访问相同的已注册能力。 |
| 产品组合 | DSH 组合包、profile、preset 和 Cordis 配置 | OpenCodex 是一项组合后的 DSH 部署。 |
| 平台集成 | 位于 DSH 所有的服务或 Host 操作背后的平台 Service Provider | Swift 或平台代码只拥有 OS 专用实现。 |
| 原生呈现 | macOS 上的 SwiftUI／AppKit，以及 iPhone 上的 SwiftUI／UIKit | 临时视图状态留在本地；产品与 agent 状态来自 DSH 事件和投影。 |

`x-native` 组合包可以拥有客户端调用 DSH 之前所需的启动发现、版本协商、设备认证、配对和传输选择。它不拥有 DSH 已表示的会话、工作区、agent、工具、审批、设置、语音领域或其他业务操作。任何保留的启动操作都必须是带有明确生命周期与安全规则的 Cordis 插件贡献；启动后，原生客户端使用普通 DSH API。

### 客户端职责

macOS 与 iPhone 应用是原生客户端，不是 WebView 壳。现有 DSH Web 客户端继续作为受支持的 OpenCodex 客户端。OpenCodex CLI 将持久化工作委托给同一个 DSH 运行时，而不是在无关实现中重新创建配置存储、插件注册表、守护进程状态或命令行为。

原生客户端实现平台导航、文本输入、无障碍、窗口与 scene 行为、通知、文件选择器、音频采集与播放、安全凭据 UI，以及其他 OS 呈现。它们消费生成或共享的协议约定和事件流。轮询、本地发明的事件类型、复制的业务 schema 和客户端专用会话模型都是需要迁移的信号，不是可接受的最终状态。

### 产品策略

- DeepSeek 是默认模型提供方；提供方选择继续使用现有 DSH 适配器扩展点。
- macOS、iPhone、Web 和 CLI 共享一份会话与任务历史。
- LAN 和 Tailscale 是首批远程传输；relay 保持为扩展点。
- 默认语音实现使用位于可替换 DSH 语音能力背后的本地高质量 STT 与 TTS Service Provider。
- Codex 与早期 DSH 数据的导入、导出和迁移进入普通 DSH 持久化模型。
- 排除宠物。首个完整交付暂缓内置图片生成，但保留其提供方扩展点。

### 证据与状态

Parity 状态分别记录证据阶段：`gap`、`implemented`、`integrated`、`behavior_verified`、`side_by_side_verified` 和 `release_verified`。只有在具名证据存在时，需求才能推进。帮助输出、复制字符串、包存在性、编译和单元测试可以支撑早期阶段，但自身永远不能产生 `release_verified`。

每项功能需求都必须能从已发布的 OpenCodex 客户端触达，通过组合后的 DSH profile 运行，在 Codex 会保持状态之处完成状态保存与恢复，并通过适用的 Codex 或 DSH 基线行为对照。发布要求在发布时刷新基线后，每项非排除需求都达到 `release_verified`。

### 第一个实现切片

第一个 macOS 切片验证架构，而不是孤立的编辑器细节。用户选择或创建工作区与会话、发送提示词、观察流式 assistant 与工具事件、处理一次真实审批、查看工具结果与最终回答、关闭并重新打开客户端，然后恢复同一个持久化会话。整个过程都使用 DSH 工作区／会话服务、`/api` 业务调用、事件流、审批服务和会话投影。

该切片先形成以 Codex 为参考的原生信息架构与交互说明。工程壳不能作为产品里程碑展示。视觉审查可以使用确定性 fixture，但验收必须使用真实组合后的 DSH 运行时和并排 Codex 工作流。

截至 2026-08-19，该产品切片已经从 DSH rc.5 前移到 rc.8。macOS 客户端实现了原生项目／任务界面、普通 DSH RPC 与 Typert Remote 适配器、Host 与 mux 事件流、重连与重新同步、事件到对话的投影、模型选择、DSH 权限选择、取消和审批响应路径。保留的 `x-native` 包将产品标识为 OpenCodex，并仅负责启动、能力发现、配对与认证；配对后的 bearer 凭据可以授权普通远程会话流量，而特权 Host 方法仍只限回环本机。DSH 继续作为持久会话与工作区状态的唯一所有者。

rc.8 TypeScript 工程图、连接／配对／语音定向测试、完整 macOS 命令行构建，以及隔离行为工作流均已通过。行为工作流会启动组合后的 DSH Host，使用隔离的持久化、sandbox、审批、工具、本地语音和模型回放服务，然后驱动 Swift 客户端完成提示词、审批、工具结果、最终回答、关闭和持久化恢复。它在不发起外部模型请求的前提下提供实现、集成与行为证据。实时提供方运行、真实 iPhone 运行和 Codex 并排对照尚未执行，因此本决策不声称已达到并排验证或发布验证。

## 考虑过的替代方案

**在 DSH 旁边构建独立 OpenCodex 内核。** 这会重复运行时，并让 DSH Web、`anchored`、持久化、工具和提供方行为成为二等集成，而不是产品基础。

**将 `x-native` 扩展成完整原生业务协议。** 这会复制现有 DSH Host API 与服务约定，为每项能力产生两条演进路径，并让原生客户端偏离 Web 与 CLI 行为。

**先生成 Codex 命令和字符串界面。** 生成的帮助与复制的字符串可以改善发现覆盖率，却无法说明可触达性、语义、持久化或交互质量。它们只保留为证据输入，而非实现。

**在原生 WebView 中交付 DSH Web 界面。** 这会复用呈现代码，但无法满足原生 macOS 与 iPhone 产品要求，也不能忠实复现平台交互、无障碍、语音、窗口或离线行为。

**为匹配 Codex 命名而重写 DSH 已有能力。** 名称属于适配器和呈现层。重新实现现有 DSH 能力只会增加状态与生命周期重复，不会改善可观察兼容性。

## 验证

- OpenCodex profile 组合现有 DSH Web 与 `anchored` 基线，并通过 Cordis 插件、组合包、preset 或平台 Service Provider 增加产品能力。
- 一份 DSH 会话事件日志和一组 DSH 服务在 macOS、iPhone、Web 与 CLI 之间保持权威；原生客户端或 CLI 的持久化存储不复制其业务状态。
- 每个保留的 `x-native` 方法都专用于启动、身份、认证或传输；业务操作使用现有 DSH 所有者和 API 路径。
- 第一个 macOS 切片完成上述从工作区到恢复会话的真实工作流，包括一次需要审批的工具调用；隔离的 rc.8 行为通道验证了该工作流。
- Parity 台账区分实现、集成、行为、对照和发布证据；缺少发布证据时，报告零项 release-verified 需求。
- 发布基线覆盖当前 Codex 桌面工作面、CLI、iPhone、远程和语音行为，以及当前 DSH Web 与 `anchored`，只移除本文明确列出的排除项。

## 后果

实时提供方、真实 iPhone 与 Codex 并排证据仍待补充；本实现决策不会推进这些 parity 阶段。

Codex 是通过观察得到的外部产品，并会独立变化，因此证据清单可能变得陈旧。即使实现未变化，发布时也必须重新捕获并进行工作流对照。

部分 DSH Host API 最初面向 Web 客户端设计，可能尚未暴露原生客户端所需的事件粒度或平台操作。解决方法是一次性扩展所属 DSH 服务或 Host 组合，而不是创建原生专用业务模型。

高保真原生 UI 工作可能过度拟合截图，却遗漏状态转换、无障碍、键盘行为或恢复。确定性视觉 fixture 和真实运行时工作流都必须通过。

现有 X 产物混合了可复用插件、重复存储、复制资源、生成界面和原型客户端。每项产物都必须得到明确的保留、重构或删除结论，之后才能为 OpenCodex 作出贡献。
